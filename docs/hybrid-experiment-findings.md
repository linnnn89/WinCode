# Hybrid 测试分支：问题与验证边界

记录日期：2026-10-06。分支：`codex/hybrid-readonly-orchestration`。

本文记录本分支迭代中实际观察到的问题、修复证据和未解决限制。实验方法、接口和原始测量表见 [只读编排实验说明](hybrid-readonly-orchestration.md)。已完成的实现提交为 `ce8b517`、`a47b6b3`、`7929cb9`、`e798f99`、`5003ad6`；本记录随测试分支提交，不改变 `main`。

## 已确认并修复的缺陷

### 1. 总 deadline 已过，错误仍归类为 WORKFLOW_ERROR

- **现象：** 真实隔离窗口的超时场景中，底层 MCP 的 `Request timed out` 先完成，而工作流自己的 timer 回调尚未执行，结果错误地返回 `WORKFLOW_ERROR`。
- **原因：** 旧实现依赖 abort 状态判断截止时间，没有同时检查实际时间是否已经达到总 deadline。
- **修复：** `e798f99` 在 [ReadonlyUiWorkflow.ts](../src/Client/ReadonlyUiWorkflow.ts) 检查实际截止时间，统一分类为 `DEADLINE_EXCEEDED`，保留完成步骤的证据并停止后续分发，不自动重试。
- **验证：** 在既有预算测试中加入可控时钟场景；修复后的真实短程基准 8 个正常样本与 7 类故障／状态场景通过，实际 helper 与 Gateway 退出检查通过。短程检查不能作为性能结论。
- **范围：** 客户端只读工作流的错误分类。它不代表所有 MCP 超时都能确定操作是否完成。

### 2. 被拒绝的观察仍能支撑“碰巧正确”的最终答案

- **现象：** 模型基准宿主接受了不满足证据要求的最终答案：查询歧义、不完整查询、节点属性读取失败、错误目标或失败配方后，只要模型给出 fixture 的正确值，就可能被判成功。
- **原因：** 旧实现过早根据底层响应登记已观察节点，未以通过完整校验的工作流报告作为登记条件。
- **修复：** `5003ad6` 在 [hybrid-model.ts](../scripts/lib/hybrid-model.ts) 只从成功的完整报告登记实际节点 AutomationId。整体失败的配方保留步骤报告，但部分步骤不能满足该配方的成功证据要求。
- **验证：** 测试先行的 12 个场景中，修复前 10 个被误判成功，另 2 个已有守卫；修复后全部符合拒绝要求。真实 WPF 响应经客户端注入歧义后，两条路径均返回 `FINAL_WITHOUT_REQUIRED_EVIDENCE`。
- **范围：** 实验宿主的结果验收缺陷。不能据此声称原生 UIA 工具读取了错误值，也不能将该守卫推广为所有第三方客户端的行为。

### 3. 未完整结束的模型回合仍会分发工具调用

- **现象：** 响应已标记截断、中断，或完成原因与工具调用不一致，但工具参数看似有效，宿主仍启动读取并继续对话。
- **原因：** 旧实现没有在工具分发前校验该模型回合的完成原因。
- **修复：** `5003ad6` 要求带工具调用的响应以 `finish_reason:"tool_calls"` 完成；无工具调用的最终回答要求 `stop`。不满足条件时返回 `INCOMPLETE_MODEL_RESPONSE`，已收到的 usage 仍保留。规则依据 [DeepSeek 官方完成原因定义](https://api-docs.deepseek.com/api/create-chat-completion/)。
- **验证：** 两条路径合计 10 个固定回复场景，修复前均启动读取；修复后均为 0 次 MCP 分发。两条路径的真实窗口回放也确认截断回复不启动 UI 读取。
- **范围：** 当前模型基准宿主的协议验收。其他提供方的兼容性尚未验证。

## 已观察到但未作为代码缺陷修复的问题

### 4. 真实模型未总能满足最终 JSON 输出契约

第三轮真实模型正式测量共 160 个样本：混合路径 80/80 通过，原生路径 77/80 通过。原生 T3 的第 10、16、19 个样本输出自然语言而非要求的最终 JSON。失败样本及其耗时、usage 均保留，没有重跑覆盖。

该报告整体为 `success:false`；T3 为 `validComparison:false`，收益百分比为 null。这是模型输出契约失败，不能报告为 UIA 操作失败。第五轮修复没有再次调用真实模型，第三轮的成功率、token 和耗时仍属于旧版验收逻辑下的历史结果，尚未用最新逻辑重新测量。

### 5. 默认测试并发下出现一次子进程退出等待超时

第五轮首次完整回归为 473/474：既有 `lifecycle-cancellation` 测试在默认并发下超过 1 秒退出等待。该文件单独运行为 14/14；最终采用项目 SDK 10.0.303、测试文件并发数 4，完整回归为 474/474。

未修改该测试的断言或无关生命周期代码。较低并发通过与资源竞争相符，但尚未确定根因；不能宣称已修复默认并发下的稳定性，也不能仅凭这次测试失败推断产品进程泄漏。首次失败日志仍保留。

### 6. 验证流程曾使用错误 SDK，并与构建发生竞争

第四轮首次回归与构建同时运行，读取产物时曾暂缺 build-manifest；该次执行还选中了系统 SDK 10.0.302，而项目固定版本为 10.0.303。这些是实际执行流程错误，不能省略后直接报告首轮全部通过。

后续先完成构建，再通过项目已有 `scripts/lib/dotnet.mjs` 验证并选择已安装的 10.0.303，相关回归通过。没有修改 `global.json` 或安装 SDK。此记录不将构建竞争归为已证实的产品缺陷。

## 已验证的守卫与实验限制

- 工具文字诱导模型调用写操作或改变目标时，实验宿主在分发前拒绝。该守卫在第五轮新增测试的首次运行就通过，属于既有行为的回归证据，不是本轮新修复的缺陷。
- 第五轮新增 3 项测试，共 24 个固定回复场景；实现修改前 2 项失败、1 项通过，修复后模型测试文件 6/6。真实 WPF 回放 6 个场景通过，4 次合法读取的 helper、Gateway 与 fixture 实际退出均已检查；没有真实模型 API 请求。
- 真实窗口回放的歧义和诱导文字由客户端注入，模型回复由本地固定序列提供。它验证宿主面对错误回复的行为，不能估计真实模型受诱导的概率，也不代表已经穷尽所有错误模型输出。
- 混合路径调用预先开发并安装的可信配方。收益包含较小的工具 schema、输出投影和部分任务的条件编排，没有测量模型生成程序或开发配方的成本，也没有隔离各项因素。
- T2 的最佳原生路径已经一次读取共同父区域，两条路径均为一次工具观察轮次。不能把 T2 的 token 减少解释成减少模型往返。
- 正式实验前已有试运行，缓存预热没有受控，两条路径的缓存命中率也不同。实际 token 可按 usage 记录，但不能直接推导普遍适用的费用或耗时优势。
- 目前证据支持继续使用客户端配方；普通 MCP 客户端对服务器 batch 的需求尚未验证，不能据此判定服务器 batch 或通用 runtime 已具备进入条件。

## 第六轮补充发现（2026-10-06）

### Off 分支的限制曾可被其他选择器绕过：已修复

新增 Off 验收时，先限制了直接按 `hybridChecks` 查询的详细读取；进一步补测发现，模型换用名称或更广的根节点查询，仍可启动额外读取。新增测试在修改前确认读取次数为 2，而约束要求只有摘要的 1 次读取。

现在摘要已被接受为 Off 后，T3 的原生后续请求只允许再次明确查询摘要，其他区域请求在分发前拒绝。相同测试覆盖名称与根节点选择器，真实 WPF 的名称选择器回放也通过。该修复只限模型实验宿主，没有收窄标准 MCP 的合法查询能力。

### 失败反馈已有针对性，但最终格式恢复仍未实现

实验宿主的工具拒绝回执现在为已知错误提供固定提示：允许的工具／配方、固定目标、JSON 参数格式、只读响应选项、源码范围，以及 Off 后应返回的结果形式。回执仍保留 `workStarted`，模型可以在后续回合根据反馈重新提出请求；宿主不自动重放旧工具计划。

模型 API HTTP／协议／取消错误仍结束样本。最终回答无法解析成 JSON 时也直接结束，没有再给模型一次格式修正机会；因此不能声称所有 LLM 失败都有纠错反馈，或已经证明这些提示提高了真实模型的下一次调用成功率。

本轮正式 On 测量共 160 个样本、359 次模型请求：混合 80/80，原生 61/80。原生 T3 为 1/20，19 次失败均在本地核对为最终 JSON 语法问题；其比较资格为 false，收益为 null。不能把本轮比第三轮更低的 T3 通过率单独归因于架构或验收收紧，模型返回版本／缓存及实际回复路径也影响结果，因果关系未隔离。

原生 T3 全部 20 次尝试共 79 次模型请求、40 次 MCP 读取、313898 个实际总 token；失败成本已汇总，不仅列一个成功样本。该问题将“有预算、对两条路径一致的最终格式纠错反馈”提升为随后需要验证的具体事项。现有数据不支持推进服务器 batch。
