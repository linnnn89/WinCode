## 1. 当前判断

**下一轮应先补齐测量与验收的可信性，再验证参数化配方在真实宿主中的使用；当前不具备推进服务器 batch 的充分证据。**

| 已有事实 | 对后续规划的影响 |
|---|---|
| 客户端工作流、参数化 `checkbox-audit`、会话及 JSON 终端入口已实现 | 继续复用，避免再造执行层或再做一次相同的固定 fixture 演示 |
| 第五轮确认并修复了证据误登记、未完整模型回合分发问题 | 第三轮数据只能作为旧验收版本的历史结果，需要明确新版规则下的证据 |
| 第三轮原生 T3 有 3 次最终格式失败 | 继续保留失败，不能仅用成功样本推导整体收益 |
| T2 原生已经一次读取共同父区域 | 该任务没有进一步减少工具观察轮次的空间；不能将 token 减少称为往返减少 |
| 模型实验直接提示使用匹配的 T1–T4 预置配方，真实 fixture 的 T3 摘要为 On | 目前没有充分验证模型自行选配方参数或在 Off 情况下终止分支的端到端行为 |
| 配方层已测试 On／Off／unknown、缺失、重复和不完整状态；终端入口已有真实会话测试 | 后续集中补模型宿主及实际使用层的缺口，不重复堆同类单元测试 |
| 默认并发回归首次 473/474，单文件 14/14，文件并发 4 时 474/474 | 保留待定位状态；不把降低并发等同于修复，也不先扩大成生命周期重构 |

原始规划中的“T2／T3 轮次至少减少 50%”门槛目前没有整体达成。后续按任务分别判断：T2 评价上下文和完整任务成本；T3 评价条件展开是否减少模型往返。这个划分用于解释结果，不追认原门槛已经通过，也不自动放行服务器 batch。

## 2. 下一轮：补齐新版验收与报告

目标是让一次新的实验能够回答“失败在哪里、失败消耗多少、哪些结果可比较”，并能把结论追溯到实际参与执行的版本。优先采用现有实验脚本中的小幅改动，不创建通用评测平台。

### 2.1 先核对旧证据能验证到什么程度

旧记录保存了每轮模型请求／响应和对模型交付的工具结果，没有单独保存统一的原始 MCP 响应流。混合路径交付的是工作流结果及投影，不能假设它包含重放当前实现所需的全部原始数据。

- 只读核查旧记录中的完成原因、最终输出格式和可见步骤证据，生成与旧结论分开的复核结果。
- 对缺少原始输入的样本标记“无法完整重放”，不补造节点、不用最终答案倒推观察。
- 若不能忠实复用 `runModelUiTask` 的输入，直接停止追求旧样本全量回放；用现有固定回复回归与新的受控测量补证据，避免写一套重复的验收器。
- 复核不发模型请求、不执行原记录中的工具计划，也不覆盖历史文件。它不能重新测得 token、耗时或模型行为。

### 2.2 报告同时保留成功样本指标与全部尝试成本

主要落点：[benchmark-hybrid-model.ts](../scripts/benchmark-hybrid-model.ts)、[hybrid-model.ts](../scripts/lib/hybrid-model.ts)。

当前比较表主要汇总成功样本，失败样本的 usage 和耗时留在逐次记录中。下一轮将这些已有数据汇总到明确的字段，避免读表时忽略失败代价：

- 计划样本、实际完成样本、通过／失败数量及失败类别。
- 成功样本的 P50／P95，以及全部已执行尝试的 token、请求数、耗时；明确分母，不将两类指标混用。
- usage 不完整时标记未知；可列已知部分与缺失数量，不把缺失计为零。
- 有失败、样本不足、执行中源码变化或清理失败时，整体状态与任务比较资格分别说明；不因为两条路径各有一些成功样本就生成收益百分比。
- 缓存命中／未命中的输入 token 按提供方实际 usage 单独统计；未返回则为未知。暂不加入会随价格变化的费用估算。
- 补齐实验身份：记录验收版本、Git revision／工作区是否有变更，核对配方、工作流及 fixture 等实际依赖的指纹是否已有覆盖；只补缺口，不重复已有构建身份机制。

公开摘要只使用固定字段白名单，不复制自由文本错误、transcript、端点、环境、绝对路径或运行标识。原始诊断记录仍留在忽略目录，不能把简单替换路径当作完整匿名化。

### 2.3 模型端到端分支场景

当前 `modelTasks` 的 T3 预期和最终所需观察都针对摘要 On：要求先观察摘要，再观察详细区域。配方本身支持 Off。需要扩展的是模型基准的任务定义和 fixture 场景，不能把固定 On 基准的限制写成生产配方缺陷。

- 用确定的 fixture 场景给出 On／Off 及独立期望值；模型任务提示不提前透露该次状态或正确计数。
- On 必须先观察摘要，再读取明确详细区域；Off 只需摘要证据，详细区域读取次数必须为零。
- unknown、歧义或不完整观察继续拒绝；保留第五轮对“碰巧正确答案”和截断工具调用的回归约束。
- 期望值来自预设 fixture 状态或独立固定样例，不复用配方统计代码作为测试预期。

### 2.4 本轮验证预算与完成条件

新增自动化测试合计最多 3 项：

1. 模型宿主的 On／Off 分支证据与调用次数；覆盖固定错误回复，确认未完成观察不能支撑最终答案。
2. 一组独立固定样本的报告聚合：成功、失败、缺失 usage、未完成计划及无效比较，核对分母和空值语义。
3. 公开摘要仅输出允许字段；用合成凭据、路径和自由文本验证敏感内容不进入摘要。

对这些具体约束先写测试，确认新场景在旧实现下的行为，再做最小修改；已有通过的守卫不为制造红灯而故意改坏。先跑相关测试与类型检查，再构建和真实 WPF 场景验收。顺序使用项目现有 SDK 选择逻辑，构建完成后再测试；完整回归靠近完成时运行一次，由本轮改动引起的失败修复后最多再完整复跑一次。

完成标准：旧证据复核范围明确；新报告不遗漏失败代价、不泄露合成敏感内容；模型宿主正确处理 On／Off；相关固定回复测试与真实 WPF 路径通过，取消及关闭后的自有进程退出已确认。该轮先完成离线与真实窗口验证，再进入真实模型测量。

## 3. 随后：有限的新测量与真实使用验证

### 3.1 重新测量当前验收版本

沿用已获授权的模型服务、当前固定目标和只读边界。执行前列出模型设置、样本数、请求／时限预算；不扩展到其他提供方或额外服务。

1. 新版固定回复和真实窗口验证通过后，先做每任务每路径 1 次的连通性检查；试运行单独记录，不并入正式样本。
2. 连通性没有阻塞问题后，先用原 T1–T4 场景进行每任务每路径 20 次、共 160 个样本的可比复测；T3-Off 等新增场景另列组别，不能悄悄混入旧 T3 指标。
3. 原有每任务最多 8 次请求、120 秒的约束继续生效。160 个样本对应最多 1280 次模型请求的理论上限，不将上限当作预计消耗；认证、协议或连续相同基础设施错误出现时应提前终止并保留部分结果。
4. A/B 使用一致的任务契约、输出格式要求、目标及观测预算。若为改善 JSON 遵从性调整提示，两侧同时采用同一规则，记录为新的实验配置；不得只修补原生侧失败样本后继续并入旧表。
5. 每个样本使用新对话、交替 A/B 顺序；预热与正式测量分开。记录实际缓存命中与返回模型身份，不声称能清空服务端缓存或固定模型别名背后的权重。

所有失败保留，不重跑覆盖；两边必须满足该任务的完整计划与正确性要求，才能给出该任务的收益结论。结果接近阈值时先报告不确定性，不自动无限增加样本。

### 3.2 验证模型能否使用参数化配方

现有基准明确告诉模型使用匹配的 T1–T4 配方，因此它证明的是“已知配方的执行收益”。下一步应在同一只读边界内验证模型选择参数的能力，并单独报告这一层增加的成本。

- 从已有 JSON 会话入口出发，选择一个参数不同的隔离 fixture 场景；模型根据用户任务给出的明确范围构造 `checkbox-audit` 参数，所有参数仍经现有校验。
- 与最佳原生调用比较，计入配方选择、参数构造、解释失败和最终回答的成本；不提前给出正确计数。
- 模型对错误参数的更正应基于新回执重新决定，不自动重放旧计划；记录恢复所需请求，禁止借此扩大目标或写权限。
- 首个非 fixture 案例在已有项目的专用测试窗口中选择，数据为合成内容。先人工确认 PID/HWND、区域和控件集合，不为完成计划扫描用户任意窗口或上传业务界面内容。
- 找不到代表性案例时，记录“真实需求尚未验证”，保持当前客户端能力，不为证明需求而扩大产品范围。

先完成一个完整案例再判断是否需要更多配方。已有配方和终端会话的基础通过结果可以复用；新增检查聚焦参数选择、原生对照以及可理解的失败反馈。

## 4. 并发超时的处理边界

该问题与上述功能主线分开记录，只有阻塞验收时才进入本轮修复范围。

- 先用已有失败日志和当前调用链区分停止请求、强制终止、操作系统退出以及测试收到退出事件的阶段；必要的本地诊断只记录阶段及耗时。
- 优先在目标测试上进行有次数上限的并发对照，不反复运行整个套件寻找一次通过。
- 只有证据证明产品清理缺陷时才改生命周期代码；若是测试调度／超时设计问题，在保持原有清理不变量的前提下修改测试。
- 在根因未明确时，文件并发 4 只是已验证的运行条件；不得删除原失败、扩大超时后直接宣称修复。
- 同一问题严格遵守最多 3 次失败的“修改—验证”循环；达到上限后停止修改，重新检查证据并做针对性资料研究。

## 5. 架构去留条件

| 决策 | 需要的证据与动作 |
|---|---|
| 继续客户端配方 | 新版验收通过，至少一个代表性实际工作流有明确需求；该任务实际总 token 降低至少 40%，或端到端中位耗时降低至少 20%，且失败代价和 P95 未抵消收益 |
| 保留 native／简化配方 | 任务原生已一次完成，或配方参数与恢复成本抵消收益；保留直接工具入口，不强迫所有任务经过配方 |
| 评估服务器只读 batch | 以上证据成立，且有明确的普通 MCP 客户端无法方便使用客户端配方的实际需求；先列出所需有限操作，复核是否能复用执行边界，再提出独立变更 |
| 评估 discovery | 实测工具目录成本仍是主要问题，且客户端可消费渐进发现；独立于 batch 评估发现失败与额外往返 |
| 评估写操作或 runtime | 当前规划不启动。必须先有现有配方／结构化 batch 无法满足的具体任务，以及独立的执行权限、未知结果与恢复设计 |

条件展开任务另查模型观察轮次能否减少至少 50%；P95 超过 10% 的恶化需解释与针对性复测。任何百分比都只适用于测量过的任务和配置。缓存不受控时不能把费用或延迟优势归因于单一架构因素。

## 6. 交付与停止点

下一轮交付限制为：实验宿主与报告的必要修改、最多 3 项新增自动化测试、相关真实窗口验证，以及现有实验／问题文档中的脱敏结果。正式模型复测和代表性使用验证按前述条件顺序开展，分别记录，不一次扩张成多个架构项目。

所有实现继续提交到测试分支。文档只保留仓库相对路径、版本、合成场景及汇总数字；原始日志保留在忽略目录，发布前检查实际待提交差异。保留无关工作区文件，不将其顺带提交。

若客户端配方已经覆盖实际需求且收益可信，就在客户端方案处完成交付；若收益不成立，就保留原生路径并停止该方向的架构扩张。完成验证后给出这一轮明确的去留判断，不以持续增加测试或继续增加层次替代结论。

## 7. 第六轮后的调整

已完成：旧记录的有界静态复核、报告聚合与公开摘要、模型宿主 On／Off 验收、3 项新增自动化测试、实际 WPF 验收及原 T1–T4 正式模型复测。旧记录缺少原始响应，未做执行重放。参数拒绝增加了针对性提示，但未做新提示与旧提示的模型纠错率对照。

正式复测的原生 T3 只有 1/20 通过，其余 19 次最终 JSON 语法失败；该任务的收益仍未成立。因此，在扩大到第 3.2 部分前，先验证有限的最终格式纠错：原生与混合采用同一提示规则、最多一次格式修正、继承原请求数和时限预算，反馈只描述输出契约，不提供正确答案，不重做已完成读取。原失败与恢复请求成本必须分别保留；错误事实、缺失证据和未完整回合不能被格式修正伪装成成功。

该事项是下一轮待实施变更，当前实现仍直接结束非 JSON 最终回答。先以固定回复和现有记录验证契约，再进行单独的小样本模型对照，避免直接重跑完整 160 个样本。达到正确性与成本条件后再继续参数化配方的实际使用验证。
