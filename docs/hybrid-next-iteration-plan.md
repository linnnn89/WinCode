## 后续执行顺序

### 工作包一：接齐 expand-ui 的父范围

范围集中在 [ExpandUiWorkflow.ts](../src/Client/ExpandUiWorkflow.ts)、既有 [SkillSession](../src/Client/SkillSession.ts)／[CLI](../src/Client/SkillSessionCli.ts) 契约及对应 Skill 用法。优先复用 [UiContracts.ts](../src/Core/UiContracts.ts) 和标准工具已实现的路径校验／解析；不新增导航服务、跨请求令牌、缓存或依赖。

1. 明确 scopePath 表示本请求已观察到的祖先范围；parentQuery／candidateQuery 相对于该范围定位。未给父级时，有限候选发现也只在该范围内进行。路径本身不负责展开隐藏的祖先。
2. 已给父级时，避免初始子查询因为旁支同名而阻断合法父范围定位，或直接把旁支同名状态当成目标结果。父级实际确认后，最终子查询使用包含该父级的路径；父选择器与路径末项三个定位字段完全一致时复用该范围根，避免重复严格后代。实际路径仍无法完整唯一解析时停止。无路径旧行为保持兼容。
3. nextRequest 保留 target、childQuery、实际父范围和已有预算；返回的局部节点不能直接冒充可跨请求使用的唯一操作身份。每个请求仍重新定位并使用现有 deadline／取消／输出限制，未知结果不重放。无新增调用时不扩大现有调用上限。

本工作包最多新增 3 项自动化测试，优先扩展既有测试数据和断言：

- 核心范围／兼容场景：覆盖有效与非法路径、初始读取、候选续接、最终子查询和 nextRequest，确认无路径有效请求保持原语义。
- 真实 WPF 双区域会话：相同父名／ID 和子 ID，在指定侧完成读取与一次展开；另一侧状态保持不变。已展开路径零额外动作，嵌套目标的最终读取不回到全窗。
- 独立失败场景：按受影响缺口选择范围失效／歧义、旧 Host 或取消，核实动作次数、结果真实性和清理；已有测试充分覆盖时不新增。固定期望来自夹具 On／Off 和未操作侧状态，不能从生产算法反推。

先运行相关测试及 npm run typecheck，再构建并走当前客户端实际入口。已有主回归和桌面测试留到工作包三集中执行；不通过 mock 透传就宣布实际范围隔离成功。涉及同一问题的修改—验证连续失败三次时停止修改，重新核对证据。

### 工作包二：一次真实应用验收

优先使用 New-tavern 现有隔离测试入口、合成配置和语音页。先只读确认实际父路径、目标身份及 UIA 能力；场景内完成目标可见时的读取、父级已展开时的零额外展开，以及折叠状态下的一次展开和独立状态读回。动作沿用用户已授权的任务范围；若只授权后台操作，就不能为通过验收擅自聚焦、键盘输入或恢复窗口。无合适隔离实例时保持 M3 未完成，不接触个人资料库凑结果。

记录实际 CLI/Gateway/Host 身份、使用的请求、完整 MCP 结果、动作次数、最终状态及自有进程退出；原始窗口数据留在忽略目录，只把脱敏方法、结果和失败追加到 [问题记录](hybrid-experiment-findings.md)。已有非 fixture 单复选框统计证据可以保留，不为同一行为重复跑模型。并列同名控件的隔离用固定 WPF 场景验证，真实应用不具备该布局时不伪造“真实应用多候选已通过”。

验收中若实际发生越界读取／操作、重复展开、把未观察状态当成功或清理残留，属于合并阻塞；先定位并修复。仅缺少非 WPF 可展开控件或未做长时性能测量，按后续范围记录。

### 工作包三：交付收尾与 PR

1. 在稳定源码上通过既有构建／检查入口生成分支产物。先核实所需 SDK 和依赖；缺失时遵守仓库安装规则，不自动更换环境。运行一次 npm run check 和一次 npm run check:desktop，二者分别覆盖核心与桌面阶段；若本次改动引发失败，修复后仅补相关阶段或一次最终复跑，不同时追加一遍 npm test 或 test:all。保留首轮失败。
2. 对 M1–M3 核对实际证据，执行 npm run delivery:verify。清单过期先比较具体差异；源码／原生产物过期按既有构建路径处理，不能只重写清单接受旧 DLL。受管 Skill 最后一次修改后再刷新并核验清单；安装副本同步、实际客户端刷新与仓库构建分别记录。
3. 更新现有文档和 CHANGELOG：说明客户端入口、显式展开及范围限制；修正根目录旧计划“UI 写操作暂不开发”和过时架构基线；完成的历史 PR 状态以新记录澄清，不抹掉原失败。公开内容排除窗口树、个人路径、模型凭据及本地附件。
4. 审查完整 main...分支差异，重点检查范围是否在每层保留、旧 Host 是否可能忽略范围、取消后是否重复动作、无关默认行为是否改变，以及实验／模型脚本是否只有显式调用才运行。按 CONTRIBUTING 记录问题处理及审查来源；不开新架构、性能或模型实验支线。
5. 实施阶段获得提交／PR 授权后，只提交相关源码、测试和文档；创建面向 main 的 PR，等待精确 head 的 Node 22/24 与 CodeQL。全部 M 条件满足并获得合并授权后合并，随后核对远端 main SHA、合并后检查与本地快进状态。若合并授权已在该实施会话给出，沿用授权，不重复询问。GitHub Release 和默认客户端部署单独执行，不由源码合并自动代表完成。

## 第十六轮：父路径内查询与展开

已实现可选 scopePath：由实际父选择器组成，逐项在上一范围内有界搜索严格后代，每一步必须完整且唯一。最终 query／setExpanded 限定在最后父级内，不带路径的既有请求沿用原流程。inspect 不带 query 时返回该父级的树；最终 query 可以匹配该根及其后代。布局 Pane 无需逐项写入，路径不会自动展开未显示的父级。

路径缺失／多义／不完整分别返回 SCOPE_NOT_FOUND／SCOPE_AMBIGUOUS／SCOPE_SEARCH_INCOMPLETE；scopeResult 保留 resolvedCount、从 0 开始的 failedIndex、status、visitedNodes 和 reason。没有退回整窗搜索。每次请求重新定位，无跨请求 COM 缓存、令牌或新增导航服务。父路径及最终查询共用已有 2 秒搜索时限，整体沿用请求 deadline／取消，未加入累计预算框架。此节保留第十六轮历史状态；当前客户端接入见第十七轮记录。

需要 inspectionVersion 5；带路径的展开先只读检查当前 Host 能力，旧版未收到动作就返回 VERSION_MISMATCH。compact 的后续查询保留 scopePath。新功能当前只暴露在标准 inspect/review/setExpanded；click/type 与 expand-ui 参数未扩展，自动路径生成和递归执行仍未实现。

### 从实际任务推导设计

用户要的是“读出这个控件的状态”，展开只是到达目标的手段。因此应优先读取已经可见的目标；目标缺失时，反馈必须说明这次看到了什么、还缺什么、哪种下一步有依据。目标未出现本身不能证明父级折叠，也不能证明操作失败。

必要证据随结论变化：执行展开需要当前唯一目标、启用证据及展开能力；确认目标属于父级需要实际结构证据；读取状态需要目标的实际状态。证明“没有其他匹配”需要完整搜索，而返回“已经观察到这些候选”可以保留局部结果并说明未完整。不能因辅助属性缺口丢掉已知事实，也不能拿局部结果宣称全局唯一。本轮只调整下表明确的路径，不将该原则扩成全项目证据策略重构。

| 当前证据 | 对用户体验的判断 | 下一轮处理 |
|---|---|---|
| `discoverParent` 先筛 Collapsed，再核对 candidateQuery | 所选区域只是正常变为 Expanded，目标仍隐藏时却收到 NAVIGATION_SELECTION_STALE；源码路径可确认，尚无独立实际窗口复现 | 按选择器重新核对该 Group 的当前身份和状态；同一有效区域 Expanded 则零展开动作，继续局部观察 |
| 展开后完整父树没有唯一目标，一律 CHILD_RELATIONSHIP_UNCONFIRMED；catch 又覆盖具体 nextAction | AI 无法直接区分“区域已经打开、内层仍折叠”“局部无目标”和“同名目标不唯一” | 保留动作后观察；用已有父树给出对应诊断和观察建议，不立即重放动作 |
| Electron 实际整窗 15 节点／12 层，Document 5 节点／4 层 | 深度主要来自外壳；增大所有任务的深度或按框架分叉都不是直接解决办法 | 优先已有 query 的局部读取；明确区分选择根节点后读取子树与真正的父范围内搜索 |
| UiQuery 只有精确名称／ID／类型和搜索数量，无父范围；节点 id 仅本次观察有效 | 看见某个内层节点，不等于下次可以按同名选择器在整个窗口唯一操作 | 本轮返回局部候选证据，不伪造祖先选择器、跨请求节点身份或“必然可执行”的内层 nextRequest |

这里有一个标准语义依据：ExpandCollapseState 描述直接子对象的显示状态，不保证所有后代可见，所以外层 Expanded 与内层仍折叠可以同时成立。[Microsoft 定义](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.expandcollapsestate?view=windowsdesktop-10.0)。原生 UIA 搜索可相对于指定元素限定范围，但 WinCode 当前尚未暴露相应父范围查询契约；不能把平台能力写成产品已实现功能。[Microsoft FindFirst](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.automationelement.findfirst?view=windowsdesktop-10.0)。

### 一个实现包，两个相连的改动

**A. 让选择续接接受有效的 Expanded 状态。** 自动首次发现仍展示可展开的 Collapsed 候选；对调用方已经选择的 candidateQuery，不再用“仍然折叠”代替身份有效性。重新核对它是否唯一、启用、具备已知展开状态：Collapsed 走现有展开一次路径，Expanded 直接观察父区域，目标已经可见则沿用现有直接读取。消失、重复或身份不匹配才是选择失效；确实禁用、必要证据未知、模式不支持分别沿用已有准确错误，不统一伪装成 stale。此处不新增用户确认，不把所有 Expanded Group 自动当作新候选。

**B. 将动作后的局部观察整理成可用反馈。** 复用当前已经取得的父树、children／parentId 和状态，优先在客户端完成，不额外扫描整个窗口。建议在现有 diagnosis 上少量增补观察范围、完整性及实际内层候选；具体字段在实施时按现有消费者确定，不预建状态机或通用导航接口。

| 动作后实际观察 | 应返回的事实和下一步 | 本次请求中的动作 |
|---|---|---|
| 父级 Expanded，完整范围内唯一目标存在 | 验证归属，独立读取实际 toggle；只有完成这些步骤才 completed | 不重复展开 |
| 父级 Expanded，未见目标，但实际发现内层 Collapsed Group | 列出名称／ID、类型、展开状态、启用情况及本次观察中的父子关系；说明是候选，尚不能证明目标位于其中 | 不自动展开第二层；AI 可依据这些证据安排后续定位 |
| 父级 Expanded，完整范围没有目标，也没有可用内层候选 | 明确“该区域未见匹配”，原因仍未知；建议检查目标查询或页面范围 | 不猜测加载中，不增加固定 sleep 或自动轮询 |
| 父级 Expanded，目标在父树中多次匹配 | 告知具体歧义，提供已有匹配信息供修正查询 | 不选第一个、不扩大动作范围 |
| 树被截断或遍历失败 | 保留已确认的父级状态与已观察节点，说明局部搜索未完成；建议缩小区域，必要时对明确截断调整一次读取参数 | 局部候选不能冒充唯一候选；不重放展开 |
| 动作调用失败／超时，尚未观察到最终状态 | 保留实际错误和动作结果未知；下一步先读取当前状态 | 不因未取得回执而自动重放 |

状态兼容：保留现有 completed／selection-required／stopped 和 success 含义；任务尚未完成仍不产生 findings。CHILD_RELATIONSHIP_UNCONFIRMED 可保留作为未确认归属的错误类别，在 diagnosis 中区分实际原因，避免为每种提示新造一个错误码。保留完整 steps；不能让统一 catch 文案覆盖已经得到的针对性诊断。已确认父级 Expanded、但任务未完成，不应被描述成“展开结果未知”。

本轮的完成体验是：AI 能说明“选定区域已经打开，因此没有再次操作；当前观察到这些内层候选／这个具体缺口”，并得到能用于下一次观察的依据。**本轮不宣称已经能自动穿过多层菜单读到最终目标。** 在当前契约尚无父范围定位时，递归执行会把局部关系丢回全窗查询，尤其容易误处理重复名称；应先消除这一真实接口缺口，再按实际案例决定是否补一条短的多层路径。

### 通用性与复杂度取舍

- 依据 UIA 能力、当前状态和观察关系处理，不检查 WPF／Electron 名称、不硬编码“高级”或具体应用 AutomationId。当前自动发现仍限 Group、结果仍限 toggle；本轮不把这项配方包装成通用菜单引擎。
- 复用 ExpandUiWorkflow、现有 CLI／会话和原生 setExpanded；不新增服务、依赖、跨请求令牌、累计预算、内部评分模型或通用工作流框架。现有超时／取消／数据上限继续工作；只有实际新增调用时才调整对应局部调用上限。
- 不要求所有 Group 的状态都完整才能认定一个已选父级有效：选择续接以被选目标的完整唯一搜索为依据，不能让无关 Group 的属性故障决定它是否可用。首次自动发现的完整性规则不在本轮全面重写。
- 直接目标读取、原生操作和既有 readonly-ui 保持各自用途。本轮不同时改只读配方的 UI／源码耦合、不增加 Tab／MenuItem／TreeItem、滚动或虚拟化导航。
- 没有新证据时不重复同一动作；有新的页面／局部观察时允许修正查询继续同一任务，不要求用户逐步批准已授权的导航。完整性要求用于支撑具体结论，不能演变成一串额外 GATE。

### 实施落点、验证与停止点

主要修改 [ExpandUiWorkflow.ts](../src/Client/ExpandUiWorkflow.ts) 的所选目标重定位、父树诊断和错误整理；复用 [UiContracts.ts](../src/Core/UiContracts.ts) 当前字段。预期无需修改原生读取器／动作器或公共 UiQuery schema；若实际必须增加父范围搜索才能满足更大目标，将其单独说明，不顺带扩入本轮。

最多新增三项有价值的自动化测试，按行为组合场景，避免为每个诊断字符串建测试：

1. **状态续接回归**：选定区域从 Collapsed 变为 Expanded 后不再 stale、不关闭、不再展开；已有目标则读到状态，目标仍隐藏则进入正确的局部诊断。覆盖无关 Group 状态缺口不阻断唯一所选目标。
2. **局部反馈场景**：有内层折叠、完整范围无目标、同名目标歧义及树截断时，分别返回真实观察和下一步；保持任务未完成，不输出猜测 findings、不进行第二次动作。
3. **真实 WPF 窗口路径**：复用现有夹具，必要时只增加嵌套区域；在已展开外层、未展开内层的真实 UIA 状态下完成客户端续接和诊断，确认外层不被关闭、内层未被意外操作。

优先先跑能复现良性状态变化被拒的测试，再改实现。已有动作结果未知、歧义、禁用与缺失状态测试按改动范围复用。相关测试／类型检查通过后构建，通过当前客户端实际 JSON 入口读完整回执并确认自有进程退出；自动夹具通过与实际客户端验收分别记录。完整回归最多一次，不重跑历史模型样本、不调用外部 API。

非 fixture 验收优先已获授权的 New-tavern 语音页：高级已展开时仍正常读取 Normalize，零额外展开。它只能验证实际单层续接，不能代替嵌套场景。第十四轮 Electron 窗口没有复选框或展开模式，不为凑兼容性结论对其执行导航；本轮若没有适合的非 WPF 导航目标，明确保留未验证，不设为整个工作包的阻塞条件。

完成后只更新对应 Skill 使用说明和本文件状态，在 findings 追加实际方法、失败和结果；不把计划写成实现。公开记录保留脱敏结果，原始窗口数据留在忽略目录。达到“已展开不误报、未完成有局部证据、无多余动作、真实入口可用”即停止。

## 历史产品约束设计复核（2026-10-06，仅文档）

以下保留 `77f4ab4` 时的评估及当时方案。第十四轮已落实其中“展开导航允许三类辅助属性缺口／原生禁用分类修正”的部分；其余条目仍为待改方向，当前状态见前部清单。

结论：当前混合 UI 流程存在部分过宽的证据门槛和试点流程限制；应按任务需要缩小阻断条件，而不是再叠加跨请求配额或授权框架。本次检查 ExpandUiWorkflow、ReadonlyUiWorkflow／Recipes、CLI 请求入口、UI 查询契约、原生 UiActionExecutor／UiTreeReader 及相关 Gateway 限制。以下是当前源码与既有记录的判断，没有新复现或性能测量；不代表已审查整个 WinCode 的所有子系统。

| 设计点 | 判断与实际影响 | 后续处理原则 |
|---|---|---|
| 所有节点／属性问题一律停止 | 过宽。发现检查所有 Group；最终取证检查全部子节点的 propertyIssues。无关 Group 或辅助 className／bounds 读取失败也可能挡住所需状态读取 | 分开任务必需证据与辅助缺口，保留原始缺口。只有身份、唯一性、归属或所需状态受影响时阻断相应结论／动作；不把不完整发现中的单个候选算作全局唯一 |
| UI 读取与源码完整性统一阻断 | 任务耦合偏强。ReadonlyUiWorkflow 在配方收到数据前统一拒绝源码扫描／代码证据省略；只需 UI 状态的任务也可能被辅助源码问题挡住 | 由任务决定是否需要源码证据。要求源码对照的任务仍检查完整性；纯 UI 任务明确报告辅助源码缺口，不因此推翻已经取得的必要 UI 证据 |
| 原生展开将所有属性问题报为 TARGET_DISABLED | 错误分类过宽。Describe 同时读取 className、isOffscreen、bounds 等；任一问题都触发该码，未区分真实禁用、启用状态未知和辅助字段缺失 | 依据展开所需身份、启用状态、操作模式和展开状态判断；辅助缺口独立反馈，不误报禁用。尚未修改原生行为 |
| 选择只接受仍为 Collapsed 的候选 | 过严的状态续接。目标已可见时已有直接读取；但目标仍未出现、所选区域已正常 Expanded 时，会被当作失效选择 | 重新观察身份和状态：同一有效父级已展开则继续读取，不再次切换；身份歧义、禁用或必要状态未知仍停止 |

### 修订后的推进顺序

1. 优先考虑一个小改动包：缩小辅助属性缺失的阻断范围，并使错误码准确表达缺失证据；先明确当前任务必需的证据，不引入通用策略引擎或新的抽象层。若进入实施，以最多三项有价值的回归和真实窗口路径确认“辅助字段缺失但必要证据有效”以及“必要证据缺失仍停止”。
2. 再考虑选择续接：有效候选已经展开时继续观察；成功展开但目标未出现时保留未完成状态并提供新证据。用候选上下文解决实际歧义，再按确有证据的内层折叠推进，不遍历全部候选。
3. 多层导航以原窗口、原任务和观察到的层级为范围；无进展或重复状态应给出针对性反馈。先复用单请求超时／取消与现有资源限制，不把跨请求累计预算列为实施门槛。只有以后实际出现重复运行失控或资源消耗问题，才重新评估是否需要累计限制。

## 2. 下一轮：补齐新版验收与报告

目标是让一次新的实验能够回答“失败在哪里、失败消耗多少、哪些结果可比较”，并能把结论追溯到实际参与执行的版本。优先采用现有实验脚本中的小幅改动，不创建通用评测平台。

### 2.1 先核对旧证据能验证到什么程度

旧记录保存了每轮模型请求／响应和对模型交付的工具结果，没有单独保存统一的原始 MCP 响应流。混合路径交付的是工作流结果及投影，不能假设它包含重放当前实现所需的全部原始数据。

- 只读核查旧记录中的完成原因、最终输出格式和可见步骤证据，生成与旧结论分开的复核结果。
- 对缺少原始输入的样本标记“无法完整重放”，不补造节点、不用最终答案倒推观察。
- 若不能忠实复用 `runModelUiTask` 的输入，直接停止追求旧样本全量回放；用现有固定回复回归与新的受控测量补证据，避免写一套重复的验收器。
- 复核不发模型请求、不执行原记录中的工具计划，也不覆盖历史文件。它不能重新测得 token、耗时或模型行为。

### 2.2 报告同时保留成功样本指标与全部尝试成本

主要落点：[benchmark-hybrid-model.ts](../scripts/benchmark-hybrid-model.ts)、[hybrid-model.ts](../scripts/lib/hybrid-model.ts)。

当前比较表主要汇总成功样本，失败样本的 usage 和耗时留在逐次记录中。下一轮将这些已有数据汇总到明确的字段，避免读表时忽略失败代价：

- 计划样本、实际完成样本、通过／失败数量及失败类别。
- 成功样本的 P50／P95，以及全部已执行尝试的 token、请求数、耗时；明确分母，不将两类指标混用。
- usage 不完整时标记未知；可列已知部分与缺失数量，不把缺失计为零。
- 有失败、样本不足、执行中源码变化或清理失败时，整体状态与任务比较资格分别说明；不因为两条路径各有一些成功样本就生成收益百分比。
- 缓存命中／未命中的输入 token 按提供方实际 usage 单独统计；未返回则为未知。暂不加入会随价格变化的费用估算。
- 补齐实验身份：记录验收版本、Git revision／工作区是否有变更，核对配方、工作流及 fixture 等实际依赖的指纹是否已有覆盖；只补缺口，不重复已有构建身份机制。

公开摘要只使用固定字段白名单，不复制自由文本错误、transcript、端点、环境、绝对路径或运行标识。原始诊断记录仍留在忽略目录，不能把简单替换路径当作完整匿名化。

### 2.3 模型端到端分支场景

当前 `modelTasks` 的 T3 预期和最终所需观察都针对摘要 On：要求先观察摘要，再观察详细区域。配方本身支持 Off。需要扩展的是模型基准的任务定义和 fixture 场景，不能把固定 On 基准的限制写成生产配方缺陷。

- 用确定的 fixture 场景给出 On／Off 及独立期望值；模型任务提示不提前透露该次状态或正确计数。
- On 必须先观察摘要，再读取明确详细区域；Off 只需摘要证据，详细区域读取次数必须为零。
- unknown、歧义或不完整观察继续拒绝；保留第五轮对“碰巧正确答案”和截断工具调用的回归约束。
- 期望值来自预设 fixture 状态或独立固定样例，不复用配方统计代码作为测试预期。

### 2.4 本轮验证预算与完成条件

新增自动化测试合计最多 3 项：

1. 模型宿主的 On／Off 分支证据与调用次数；覆盖固定错误回复，确认未完成观察不能支撑最终答案。
2. 一组独立固定样本的报告聚合：成功、失败、缺失 usage、未完成计划及无效比较，核对分母和空值语义。
3. 公开摘要仅输出允许字段；用合成凭据、路径和自由文本验证敏感内容不进入摘要。

对这些具体约束先写测试，确认新场景在旧实现下的行为，再做最小修改；已有通过的守卫不为制造红灯而故意改坏。先跑相关测试与类型检查，再构建和真实 WPF 场景验收。顺序使用项目现有 SDK 选择逻辑，构建完成后再测试；完整回归靠近完成时运行一次，由本轮改动引起的失败修复后最多再完整复跑一次。

完成标准：旧证据复核范围明确；新报告不遗漏失败代价、不泄露合成敏感内容；模型宿主正确处理 On／Off；相关固定回复测试与真实 WPF 路径通过，取消及关闭后的自有进程退出已确认。该轮先完成离线与真实窗口验证，再进入真实模型测量。

## 3. 随后：有限的新测量与真实使用验证

### 3.1 重新测量当前验收版本

沿用已获授权的模型服务、当前固定目标和只读边界。执行前列出模型设置、样本数、请求／时限预算；不扩展到其他提供方或额外服务。

1. 新版固定回复和真实窗口验证通过后，先做每任务每路径 1 次的连通性检查；试运行单独记录，不并入正式样本。
2. 连通性没有阻塞问题后，先用原 T1–T4 场景进行每任务每路径 20 次、共 160 个样本的可比复测；T3-Off 等新增场景另列组别，不能悄悄混入旧 T3 指标。
3. 原有每任务最多 8 次请求、120 秒的约束继续生效。160 个样本对应最多 1280 次模型请求的理论上限，不将上限当作预计消耗；认证、协议或连续相同基础设施错误出现时应提前终止并保留部分结果。
4. A/B 使用一致的任务契约、输出格式要求、目标及观测预算。若为改善 JSON 遵从性调整提示，两侧同时采用同一规则，记录为新的实验配置；不得只修补原生侧失败样本后继续并入旧表。
5. 每个样本使用新对话、交替 A/B 顺序；预热与正式测量分开。记录实际缓存命中与返回模型身份，不声称能清空服务端缓存或固定模型别名背后的权重。

所有失败保留，不重跑覆盖；两边必须满足该任务的完整计划与正确性要求，才能给出该任务的收益结论。结果接近阈值时先报告不确定性，不自动无限增加样本。

### 3.2 验证模型能否使用参数化配方

现有基准明确告诉模型使用匹配的 T1–T4 配方，因此它证明的是“已知配方的执行收益”。下一步应在同一只读边界内验证模型选择参数的能力，并单独报告这一层增加的成本。

- 从已有 JSON 会话入口出发，选择一个参数不同的隔离 fixture 场景；模型根据用户任务给出的明确范围构造 `checkbox-audit` 参数，所有参数仍经现有校验。
- 与最佳原生调用比较，计入配方选择、参数构造、解释失败和最终回答的成本；不提前给出正确计数。
- 模型对错误参数的更正应基于新回执重新决定，不自动重放旧计划；记录恢复所需请求，禁止借此扩大目标或写权限。
- 首个非 fixture 案例在已有项目的专用测试窗口中选择，数据为合成内容。先人工确认 PID/HWND、区域和控件集合，不为完成计划扫描用户任意窗口或上传业务界面内容。
- 找不到代表性案例时，记录“真实需求尚未验证”，保持当前客户端能力，不为证明需求而扩大产品范围。

先完成一个完整案例再判断是否需要更多配方。已有配方和终端会话的基础通过结果可以复用；新增检查聚焦参数选择、原生对照以及可理解的失败反馈。

## 4. 并发超时的处理边界

该问题与上述功能主线分开记录，只有阻塞验收时才进入本轮修复范围。

- 先用已有失败日志和当前调用链区分停止请求、强制终止、操作系统退出以及测试收到退出事件的阶段；必要的本地诊断只记录阶段及耗时。
- 优先在目标测试上进行有次数上限的并发对照，不反复运行整个套件寻找一次通过。
- 只有证据证明产品清理缺陷时才改生命周期代码；若是测试调度／超时设计问题，在保持原有清理不变量的前提下修改测试。
- 在根因未明确时，文件并发 4 只是已验证的运行条件；不得删除原失败、扩大超时后直接宣称修复。
- 同一问题严格遵守最多 3 次失败的“修改—验证”循环；达到上限后停止修改，重新检查证据并做针对性资料研究。

| 决策 | 需要的证据与动作 |
|---|---|

### 9.2 实施顺序和改动落点

### 9.3 参数反馈与重试规则

下列增量契约在规划中提出，现已按本节边界实施。已知配方输入错误统一为 `INVALID_RECIPE_PARAMETERS`，未知配方为 `UNSUPPORTED_RECIPE`；具体字段使用 `field`、`errorMessage`、`recoveryAction` 描述。错误分类放在参数校验处产生，CLI 和模型宿主不维护两套规则。

| 情况 | 给模型的反馈 | 后续动作 |
|---|---|---|
| 控件列表为空、重复或超限 | 固定字段 `checkboxAutomationIds`、数量／唯一性要求 | 可根据原任务重新提交一次合法列表；不得自行删除任务要求的控件 |
| AutomationId 或预算非法 | 对应合法字段路径、允许类型和范围 | 可修正格式／预算；不得自动扩大到整窗读取 |
| 未知字段、配方或写入参数 | 支持的配方／字段集合与只读要求 | 不执行；只有保持任务范围的修正才可继续 |
| 目标、区域或控件集合偏离原任务 | 明确任务范围不匹配 | 本实验结束该样本，不将越界尝试作为普通参数优化继续 |
| 已执行读取但观察歧义、缺失、unknown 或不完整 | 保留已有错误、实际执行阶段与证据 | 结束样本；不通过删控件、猜结果或追加范围使其通过 |
| 已有有效观察，最终 JSON 格式错误 | 第七轮既有格式反馈 | 最多一次格式修正，禁止新的工具调用 |
| HTTP／协议错误、取消或总时限耗尽 | 保留失败类别与已知成本 | 结束样本，不重试 |

只有校验明确发生在执行之前时才报告 `workStarted:false`；传输失败或结果未知不能一律标为未执行。`recoveryAction` 表示调用方可考虑的下一步，不授权宿主自动重放。

参数更正上限为每个样本一次，最终格式更正沿用一次；两者共享最多 8 次模型请求、120 秒总时限和既有上下文／输出预算。更正由模型在读取回执后重新决定，宿主不改写错误参数、不代填答案。达到上限就记录失败。两条路径采用相同的输入错误机会与总预算；原生侧仍可使用最佳合法 scoped query。

错误内容只输出固定代码、允许字段名及不含输入值的提示，不回显完整拒绝参数、任意键名、凭据、端点或环境。旧 `requestError` 继续可读；新增信息不要求已有客户端立即升级。

### 9.4 固定场景与独立验收

只研究“明确选定复选框的状态汇总”这一类任务，使用现有窗口的三种配置。下列期望仅供宿主验收和测试，不放入模型提示；模型只获得任务范围、输出契约和可用工具说明。

| 场景 | 用户明确范围 | 独立预期 | 每次合法执行的 UI 读取 |
|---|---|---|---|
| P1：无条件子集 | `hybridChecks` 内的 `hybridCheck0/3/6`，不提供摘要参数 | checkedCount=2，unchecked=[hybridCheck3]，disabled=[hybridCheck6] | 原生和配方各 1 次 |
| P2：摘要 On 的另一子集 | 先判断摘要，再统计 `hybridCheck1/2/3/5/6` | detailsRequired=true；checkedCount=4，unchecked=[hybridCheck3]，disabled=[hybridCheck6] | 原生和配方各 2 次；模型观察轮次可不同 |
| P3：摘要 Off | 与 P2 相同范围，fixture 启动为 Off | 仅 detailsRequired=false | 原生和配方各 1 次，详细读取为 0 |

共同区域中的其他控件属于读取上下文，不能进入选定集合的统计。验收检查模型实际提交的目标、区域、控件集合和最终证据，不能只检查结果中的数字；即使 Off 不会读取详情，错误的任务参数也不得因为最终 false 正确而通过。明确集合可允许顺序变化，但成员、条件与目标必须一致。

A 为原生 inspect，B 为现有参数化客户端配方。两边收到相同任务范围，不要求原生逐个读控件；原生可一次读取共同父区域。底层仍经过同一标准 MCP、固定 PID/HWND、backgroundOnly、capture:none 与现有结果完整性校验。

这三个场景验证参数迁移与条件执行，仍属于合成 fixture。它们不证明模型能从任意自然语言发现控件，也不替代非 fixture 实际应用验收。

### 9.6 真实模型预算及统计口径

先完成上述确定性检查，再使用现有已授权的提供方和设置。开跑前固定源码、场景定义、工具 schema、任务提示及验收版本；不得在一组数据中途修改实现。

- 连通性检查：P1–P3 × 两条路径 × 1 次，共 6 个样本，独立记录。
- 主小样本：P1–P3 × 两条路径 × 5 次，共 30 个样本；交替 A/B 顺序，并轮换场景顺序。总计最多 36 个样本、288 次模型请求的理论上限，不把上限当预计消耗。
- 每样本最多 8 次请求、120 秒；一次参数更正与一次最终格式更正均从该预算扣除。认证、协议或基础设施阻塞即停止整组并保留部分结果；任务级失败照实计数。
- 不为得到恢复样本故意篡改真实模型参数。自然发生的输入错误才计入真实恢复率；没有发生则报告“未观察到可恢复参数错误”，固定回复测试仅证明宿主规则。

完整任务成本包含 schema、参数生成、被拒绝请求、工具回执、纠错与最终回答；同时保留各恢复阶段的请求／耗时／usage。usage 不完整则相关总量为 null，并列已知部分；缓存命中按提供方实际返回统计。`firstPassPassed` 的语义变化必须通过新验收版本明确说明，不能悄悄沿用旧“没有格式纠错”的含义。

## 10. 第八轮实际结果与停止点

已实现：共享的参数校验错误、兼容原协议的 CLI 增量回执、模型实际参数分发、任务范围与证据约束、一次参数更正、与最终格式更正分开的计量，以及 P1–P3 独立报告。新增 3 项测试，最初全部红灯；补测并修复未知状态／实际观察不支持固定场景答案的验收缺口。相关测试 18/18，真实会话文件 6/6，主回归 482/482；后来明确参数提示后相关 18 项及类型检查再次通过。新增会话测试最后补齐条件子集和审计 helper 退出，单独通过。没有再次完整回归，也没有追加模型样本。

真实模型按预算执行 6 个独立试运行和 30 个独立小样本，全部 70 次请求、200489 个 token；试运行 3/6，小样本原生 12/15、混合 3/15。小样本混合侧 12 次将参数打印为最终 JSON，没有实际工具调用；原生 Off 有 3 次试图读取详情而被拒绝。三种场景均不能给出收益百分比，整体模型验收未通过。7 次最终格式失败恢复属于格式纠错，不能混称参数恢复；本轮真实参数更正机会为 0。

本轮完成了实现与确定性／真实入口验证，以及有成功和失败的有限实验；没有完成“模型参数化调用稳定可用”或非 fixture 迁移。当前停止追加模型调用，保留原生入口和实验分支。下一次改良首先针对已经确认的“构造参数被当成最终回答”区分工具调用与最终结果的契约，再以独立配置验证；任何新的样本预算需先列明，不能覆盖本轮失败或自动执行最终 JSON。该缺口解除前，服务器 batch 与进一步实际应用模型迁移的进入条件仍不满足。
